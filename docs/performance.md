# Performance — measured, against the blueprint's dataset

§26 sets targets for ordinary page reads and asks for findings "against the
actual plan and dataset". Until 18 October 2026 nothing here had met more than
a handful of rows, so every performance statement in this repository was a
guess. These are measurements.

## What was measured, and on what

| | |
| --- | --- |
| Dataset | 50 organisations, 5,000 leases, **300,000 charge documents and lines**, 284,862 receipts, 284,862 allocations, 1,169,724 journal lines, five years of monthly billing. 1,055 MB |
| Generated by | `pnpm db:loadgen`, which provisions each organisation through the real command and then writes the bulk rows set-based, verifying the result against the same invariants the restore rehearsal checks |
| Application | Production build (`next build` / `next start`), not a development server |
| Database | PostgreSQL 16 on the same machine, default configuration |
| Measured by | `pnpm perf` — a real sign-in including the second factor, then five navigations per screen |
| Hardware | A shared development container. **Not production-class, and these numbers are not a customer's experience.** What they bound is the product's own query behaviour at this data volume |

The organisation measured holds 100 units and five years of charges — the
per-tenant scale that decides what a page costs.

## Results

Time to the content an operator came for, median of five runs, after the fixes
below. The raw figures, including the slowest run of each, are in
[`perf-results.json`](perf-results.json).

| Screen | Median | Slowest | §26 target (1s) |
| --- | ---: | ---: | --- |
| Portfolio | 173ms | 187ms | met |
| Audit trail | 211ms | 437ms | met |
| Residents | 218ms | 284ms | met |
| Collection report | 427ms | 433ms | met |
| Reconciliation | 428ms | 446ms | met |
| Rent roll | 440ms | 493ms | met |
| Leases, page 1 of 5,000 | 484ms | 526ms | met |
| Lease account (five years of history) | 491ms | 496ms | met |
| Arrears ageing | 534ms | 557ms | met |
| Overview | 948ms | 1,469ms | met, with the least room |

**All ten screens meet the target.** The two that did not are the two that
moved most: the collection report from 3,003ms to 427ms, and the overview from
2,532ms to 948ms. The overview is now the slowest screen in the product and the
one worth looking at next; it reads eight separate measures and a queue, and
none of them is slow on its own.

A note on what is NOT being reported. Time to first byte sits at 30–150ms on
every screen, because the server streams the page shell before the data is
ready. It is a real number and a useless one: it measures the shell, not the
read §26 is about. The figures above are time until the content is on screen.

## What was fixed, and what it was worth

Every figure below is before and after on the same dataset and the same
machine. All of them came from reading plans and the slow-query log.

| Screen | Before | After the query fixes | After the policy fix (0057) |
| --- | ---: | ---: | ---: |
| Leases, page 1 | 3,043ms | 552ms | 484ms |
| Rent roll | 2,974ms | 728ms | 440ms |
| Reconciliation | 2,964ms | 908ms | 428ms |
| Arrears ageing | 973ms | 584ms | 534ms |
| Overview | 3,026ms | 2,532ms | 948ms |
| Collection report | 3,451ms | 3,003ms | 427ms |

1. **The balance views could not use the indexes built for them** (migration
   0053). `lease_balances` totalled a lease's charges with a lateral filtered on
   `lease_id` alone. Every index in this schema leads with `organisation_id`,
   because every query in this product is about one customer — so the leading
   column was unconstrained, the index was unusable, and the plan read:

   ```
   Seq Scan on charge_lines cl
     Filter: (lease_id = l.id)
     Rows Removed by Filter: 299940
     loops=100
   ```

   Thirty million rows examined to total a hundred leases. Adding the
   organisation to each lateral changes no result — a lease's charges belong to
   that lease's organisation, and the composite foreign keys make anything else
   impossible — it only tells the planner what the schema already guarantees.
   The view went from **2,400ms to 75ms**, and four screens with it.

2. **The lease picker read the whole ledger once per lease.** The reconciliation
   screen's "whose payment is this?" dropdown computed each lease's outstanding
   balance with a correlated subquery — five hundred passes over the open
   charges to fill one list. It is now a single grouped pass joined to the page.

3. **The leases list computed balances for every lease, then showed fifty.**
   `lease_balances` was joined before the `limit`. The page is chosen first now.

4. **Joins to `charge_documents` repeat the organisation** (collection metrics,
   allocations), which removed a sequential scan of all 300,000 documents from
   those plans.

### A mistake worth keeping in the history

Migration 0053 also replaced the allocation index — `(charge_line_id)` where not
reversed — with an organisation-leading version, on the same reasoning that had
just been right about the laterals. It was wrong here: the allocation lookup
*inside* the view filters on the charge line alone, so the leading column went
unconstrained and the lookup fell to a sequential scan of every allocation in
the database, six thousand times per read. **The view went from 2,400ms to
194,000ms** — eighty times worse than the problem being fixed.

It was caught immediately, by measuring instead of assuming, and 0054 puts the
index back with a covering column. The lesson is in the migration: the fix for a
missing predicate is to add the predicate, not to move the index out from under
the query that was using it correctly.

### The policies cost more than the queries (migration 0057)

The two screens that missed the target were both the collection metrics — the
summary on the overview, the per-lease table on the report. The guess recorded
here last time was that the combined statement had the wrong shape. That was
wrong, and the way it was established is worth keeping.

The query was timed twice against the same data, on the same machine, in the
same second: **27ms** as the database owner, **1,300ms** as the application
role. The data work was never the problem. Row Level Security was.

Every policy in the schema was written as a function call on the row:

```sql
using (app.is_org_member(organisation_id) or app.has_support_access(organisation_id))
```

`app.is_org_member` is STABLE, but its argument changes with every row, so
Postgres calls it per row — a query against `memberships` for each of six
thousand charge lines. The resident policies were worse: being separate
PERMISSIVE policies they are OR-ed in, and two of them wrapped a *correlated*
EXISTS around a second table, which brought that table's own policies with it.
One join of ninety-four allocations to their charge lines cost 878ms.

The fix is the shape, not the logic. A set the caller belongs to is computed
once per query and hashed:

```sql
using (organisation_id in (select app.member_organisation_ids()))
```

Same rows, same rules — active membership, live support session, unexpired
portal link — evaluated once. Measured on that same join: **878ms to 38ms**.
Measured end to end on the two screens that failed:

| | Before | After |
| --- | ---: | ---: |
| `collectionTotals`, under the app role | 1,699ms | 217ms |
| `collectionByLease`, under the app role | 1,343ms | 138ms |

Nothing about the collection query itself changed. The index this work was
expected to need was built, measured, found unused, and dropped again.

Two things keep it from coming back. `tests/db/schema-invariants.test.ts` fails
if any policy calls one of those helpers on a row, and the isolation suites —
which did not change — are what prove the rewrite kept every rule it found.

## What is still slow, and why

Nothing is over the §26 target. The overview is the closest at 948ms, and it is
the next thing worth reading plans for: eight measures and a queue, none slow
alone.

Also not done, and worth saying plainly:

* **No concurrency.** Every measurement here is one user at a time. Nothing is
  known about this product under ten operators, let alone a hundred.
* **No write measurements.** Posting a billing run over 5,000 leases has not
  been timed.
* **No production-class hardware.** Managed Postgres with provisioned IOPS and
  a separate application host will not behave like this container, in either
  direction.

## Repeating this

```bash
psql -c 'create database propertyos_load'
DATABASE_URL=...propertyos_load pnpm db:migrate
DATABASE_URL=...propertyos_load pnpm db:loadgen          # ~14 minutes
DATABASE_URL=...propertyos_load APP_DATABASE_URL=...propertyos_load \
  NODE_ENV=production pnpm --filter @propertyos/web build
#   ... then next start -p 3100 with the same environment
DATABASE_URL=...propertyos_load APP_BASE_URL=http://127.0.0.1:3100 pnpm perf
```

`pnpm db:loadgen` takes `--organisations`, `--units`, `--months` and
`--database`. It refuses to run against a database whose name does not say what
it holds.

For iterating on one query rather than ten screens, there is a smaller tool
that calls the same domain functions through `withActor`, so the policies and
the permission resolution are production's:

```bash
DATABASE_URL=...propertyos_load APP_DATABASE_URL=...propertyos_load \
  pnpm --filter @propertyos/worker exec tsx src/collection-timing.ts
```

Point it at the app login role, not the owner — the difference between those
two is the whole of the finding above.
